# tudouni-aigo · desktop

The Tauri 2 + React desktop client. It drives the **existing** Go runtime as
separate processes over the same JSONL stdio protocol the TUI uses — this is a
different front end, not a second kernel.

```
┌─ Tauri 2 app ─────────────────────────────────────────────┐
│  WebView (React 19 + Vite)   ←→   Rust shell              │
│  UI, state, i18n                  process, IPC, window    │
└──────────────────────────────────┬────────────────────────┘
                                   │ stdin/stdout: JSONL, one line per message
              ┌────────────────────┼────────────────────┐
   tudouni-aigo --runtime-stdio            …one per session…
     cwd = workspace A                      cwd = workspace B
              │                                        │
   agent loop / tools / permissions / model   (its own)
```

**One session, one child process.** A workspace is the child's working
directory and `--session` names the conversation, so a session is a process
rather than something a message can move — and two of them run in parallel by
both existing at once. The bridge mints a `ChildKey` for each, tags every event
with it, and the front end keeps one bucket of runtime facts per key. The
protocol and the runtime are unchanged by this; the full reasoning, the
alternatives and the shared-file analysis are in
`../tudouni-aigo-desktop-design/multi-session-parallel.md`.

Authority for everything below: `../tudouni-aigo-desktop-design/desktop-app.md`,
the design system under `../tudouni-aigo-desktop-design/tudouni-aigo/`, and — for
protocol shapes — the Go source and `protocol/schema/*.json` in the repository
root.

## Running it

```bash
npm install
npm run runtime:stage   # put the Go runtime next to the app (see below)
npm run tauri dev       # the real thing: window + child process

# without a window — the UI runs in a browser, no runtime starts:
npm run dev

# checks
npm run build           # tsc -b + vite build
npm run typecheck       # tsc -b
npm test                # protocol / projection / stream-reducer tests
npm run audit:css       # every className has a CSS rule
```

Requires Node ≥ 20. `npm run tauri *` additionally needs a Rust toolchain and,
on Windows, the MSVC linker.

`npm run tauri build` produces a packaged app.

### Staging the runtime first

The app does **not** embed the runtime; it spawns it. So the binary has to exist
before the window will work:

```bash
make release            # from the repository root — stages dist/<version>-<triple>/
npm run runtime:stage   # copies it into src-tauri/runtime/
```

`runtime:stage` copies the binary, `prompts/`, `config.example.json` and the
vendored ripgrep, matching the layout `make release` stages. The layout matters:
the runtime decides "am I in a package root?" by looking for a `prompts`
directory, and a miss is **silent** — the program starts and the `grep` tool
simply disappears.

Those files are not committed (an 18 MB binary plus a 4 MB ripgrep, both
regenerated by `make release`, and committing them would let them drift from
`VERSION`). If you would rather not stage them, point the bridge straight at an
existing build instead:

```bash
# PowerShell
$env:TUDOUNI_RUNTIME = "<repo>/dist/tudouni-aigo-<version>-<triple>/tudouni-aigo.exe"
npm run tauri dev
```

In a plain browser the IPC surface is absent, so the bridge reports itself
unavailable and the UI stays in its "starting" phase rather than pretending to
have a runtime. Everything that does not need a child process — layout, panels,
stream reduction — is still exercisable that way.

### Pointing it at a runtime

The Rust side resolves the binary in this order, and **never** through `PATH`:

1. `TUDOUNI_RUNTIME` — an absolute path, for development;
2. `runtime/tudouni-aigo[.exe]` next to the app, or one to three directories up
   (a packaged bundle puts it in `resources/runtime/`).

A different build on `PATH` is a different program, and the symptom is a child
that exits immediately. So the path is always explicit.

The workspace is the child's working directory, because the runtime takes its
`cwd` as the workspace and the file tools' boundary is exactly that. The
directories the runtime refuses (home, a volume root, an ancestor of home) are
rejected here too, with a message — otherwise the refusal arrives as an exit code
2 after writing to a stderr nobody is reading.

**Where the first session opens is never decided by where the app was started.**
That used to be the fallback: a launch with no workspace passed the bridge
nothing, and the bridge read "nothing" as `std::env::current_dir()` — which for a
packaged application is its own install folder. The session file is not there,
and the runtime reads a session id with no file as *a new session with that
name*, so the window came up in a directory nobody chose and nothing failed
loudly. So the rule is now explicit, and there is no fourth case:

1. **Something was remembered and still works** → the first session opens there.
2. **Something was remembered and no longer works** — deleted, unmounted, or a
   directory the runtime refuses (home, a volume root, an ancestor of home) →
   **no child is started**, and the reason is printed on the first screen, which
   stays usable because the workspace list beside it never depended on it.
3. **Nothing was remembered** (a first launch) → nothing is started, and the
   first screen asks. There is no honest directory to guess.

The remembered value is `lastWorkspace` in `localStorage`, written from
`init.workspace` — the runtime's own answer about where a session is — and never
from a path the front end assembled. It follows the session you are *looking at*,
so a background conversation's `init` cannot move it. It is deliberately not
cleared when its directory disappears (a drive can be plugged back in); picking a
workspace overwrites it, and the check at start-up reports it.

The same rule protects every later attach: with no caller-named workspace, no
active session, and nothing remembered, `attachSession` **refuses** rather than
letting the bridge fall back. See `resolveAttachWorkspace` in `state/store.ts`.

Directories the runtime refuses (home, a volume root, an ancestor of home) are
rejected before the child starts, so the refusal is a sentence rather than an exit
code 2 written to a stderr nobody is reading.

## The rules this implementation keeps

**Every number on screen comes from a protocol message.** The projection layer
(`runtime/adapt.ts`) maps; it does not derive. Where a fact is missing it says
`null` and the view renders "unknown" — a plausible wrong value is worse than a
visible gap.

**No optimistic updates.** Pressing "always allow" sends one outbound message and
nothing else. The display changes when `ui(state)` comes back. Anything else
makes "the screen says on, it is actually off" possible.

**Two groups of state, strictly apart.** Runtime facts are written only by
`applyRuntimeMessage`. Preferences (quiet mode, sidebar and block folding, the
draft, history, **the workspace list**) belong to the front end and never enter
the protocol.

**The left rail manages places and conversations, and nothing else.** Workspaces
and sessions, in that order, because that is the order of the decision. The two
halves differ in where their facts come from and the difference is load-bearing:

- The **workspace list** is a preference. The protocol has no workspace list and
  could not usefully carry one — a workspace *is* the child's working directory,
  so changing it is a different process, not a message. What the runtime *does*
  state is which workspace is **current** (`init.workspace`), and that is what
  marks a row. So a bookmark the runtime is not in is simply not current;
  "listed" and "current" are never conflated. Adding or forgetting one sends
  nothing.
- The **session list** is entirely the runtime's: `sessions.items` answers
  `session_list`, and opening one is either **focusing the child that already
  holds it** (which sends nothing at all) or **starting a child on it**.
  `messages`, `steps`, `todos` and `preview` are all computed by the runtime;
  this rail counts nothing itself and never reads a session file.

  **This rail does not send `session_switch`.** That message makes the runtime
  rebuild itself and call `pending.abandonAll()`, which is exactly what stopped
  two conversations from running at once. The protocol keeps it for the TUI and
  the CLI; here, a conversation is a process.

**A session is a process, so the rail can show what each one is doing.** Each
row carries a status dot at its left edge — asking, broken, running, or
finished-and-unlooked-at — and a workspace row carries a count of the sessions
inside it that want a person. Without that, opening a second conversation would
be a way to lose track of the first: the dot is the only place that answers "is
anything waiting for me" while you are looking at something else. Colour is
never the whole signal (every dot has an accessible name), the dots do not pulse
(`component-states.md` §7, and several of them breathing at once is noise rather
than a continuing condition), and a session that is merely idle draws nothing.

Neither a sign-in nor a plugin market is drawn. There is no account behind this
window and the runtime has no plugin registry — its extensibility is MCP servers
and skills, which are the right-hand sidebar's business. A control for either
would be a control for something that cannot happen.

The rail's actions are inert while a blocking prompt is up, and one of them
still has to be: starting a new session under a prompt is a way to lose track of
what is waiting. What is **gone** is the old blanket rule, which existed because
switching a session abandoned the request the runtime was blocked on. Focusing a
session sends nothing now, and answering a prompt goes back to the session that
asked — so with two conversations waiting, both can be answered.

**The two blocking modals are fail-closed.** No auto-skip, no timeout, no
guessing. Approval shows the arguments in full and the runtime's two hints
verbatim; "always allow" appears only when there is something to remember, and
"allow all" only when the runtime set the flag. For a question, `options` is a
`string[]` and an empty array means free-form; skip is its own action and Esc
resolves to it.

**Interface copy is English only.** The runtime is English-only by construction
(`internal/i18n`: "This build speaks English only", with the language-switching
machinery removed on purpose), so a second language here would promise something
the thing behind it cannot deliver. Text the runtime wrote — a `notice`, a
`remember_hint` — is displayed **verbatim**, never translated: translating it
would invent a second source for the same fact and break the rule that those
hints are not altered by a character.

**One theme, the system's.** No in-app switch (the native spec requires a single
source, and `init` carries no theme list), which is also why `/theme` is not in
the command table — that table has 17 entries, not 18. The runtime's `--theme`
flag is the *TUI's* palette and is deliberately not wired in.

**Images are attached by writing their path into the sentence.** That is the only
channel that exists — the runtime recognises a path in the text itself; there is
no upload command and no markup. Everything below is a way of getting a path into
the sentence, never a way of shipping bytes down a channel that is not there.

Three ways in, and they differ only in where the path comes from:

| Way in | What it does |
| --- | --- |
| Type it | The original mechanism. Nothing in the front end is involved. |
| **Drop** a file | Inserts the absolute path Tauri hands over. |
| **Paste** a picture | Writes the clipboard's bytes into the workspace and inserts the **workspace-relative** path. |

Two things about the drop path are easy to get backwards:

- **`dragDropEnabled` must be `true`** in `tauri.conf.json`, despite the name.
  `true` is what makes Tauri take the OS drop, so the WebView does not navigate
  to the file and `onDragDropEvent` hands over **real absolute paths**. Setting
  it to `false` switches to HTML5 drag-and-drop, which on Windows deliberately
  withholds the path (`DataTransfer.files` gives a `File` with a name and no
  location) — the feature becomes impossible, which is what `false` plus the
  missing handler used to amount to.
- **The handler is at the window level** (`hooks/useFileDrop.ts`), not on the
  composer: a drop can land anywhere in the window, and only a real path can be
  checked against the workspace.

### Pasting a picture

A screenshot from `Win+Shift+S`, or an image copied out of a browser, reaches the
clipboard as **bytes** — and a WebView has no filesystem. So the bytes go to the
Rust side (`image_stash`, sent as a raw request body rather than base64), become
a file under `<workspace>/.tudouni/paste/`, and the returned path is written into
the draft. From there it is the ordinary mechanism: the runtime scans the
sentence, resolves the path inside the workspace, and attaches the picture.

Five things worth knowing before changing any of it:

- **A paste of text must keep behaving exactly as it did.** The handler returns
  before `preventDefault` unless the clipboard really holds an `image/*` item, so
  pasting a sentence, a path or a snippet is untouched. This is the regression the
  feature can least afford — the composer is the one control a person uses
  constantly.
- **The file goes under `.tudouni/`, not into the project tree.** It has to be
  *inside the workspace* (`Workspace.SafePath` is the boundary, so `%TEMP%` would
  produce a path that can never be attached), and it must not show up in
  `git status`. That directory is cleared on every start, which is safe because it
  is a **staging area**: a picture that was sent already lives in the runtime's
  content-addressed artifact store.
- **The bytes decide the format**, never the clipboard's declared type — a `.png`
  that is really a JPEG is common, and the runtime sniffs the same way.
- **The chips are derived from the draft text** (`ImageTray` +
  `referencedImages`). The text is the only thing that gets sent, so deleting a
  path drops its chip, and a chip can never claim a picture that is not going
  anywhere. Dismissing a chip edits the **sentence**, not a list of attachments.
- **`referencedImages` is a port of the runtime's scanner**, not a `includes`
  check. A path in a sentence may be wrapped in punctuation or glued to Chinese
  prose, so the runtime offers several readings and lets the filesystem pick —
  and the tray has to agree with it in both directions, or it would miss an
  attachment that happened or claim one that did not.

`Ctrl+V` is the only entry point. There is deliberately **no attach button**: the
DOM cannot read a picture off the clipboard on demand, so a button would need the
clipboard plugin and would sometimes do nothing — worse than no button.

> **On Linux**, pasting image *data* may not work at all: WebKitGTK could not read
> an `image/*` clipboard entry until WebKit commit 301877 (2025-10-21), so an
> older system WebKitGTK yields no items and nothing is pasted. Windows/WebView2
> is unaffected. The fallback would be `tauri-plugin-clipboard-manager`, which
> returns RGBA pixels rather than PNG bytes and would need an encoder as well.

### 21 · Why the close prompt has a deadline, but the person does not

`CloseRequested` **refuses the close** and asks the front end to draw a dialog,
because every overlay here is DOM and a native dialog would be a second visual
language for one question. That refusal is what makes a deadline necessary: a
window that hands its closability to another process needs a way back if that
process is wedged, or a renderer that never mounted the dialog would trap the
window on screen for good. So Rust arms a five-second watchdog on the **round
trip**.

It must not be a deadline on the person. The prompt offers to remember the
choice, so reading it before answering is the expected behaviour rather than an
edge case — and a window that closed itself while somebody was deciding would be
worse than no prompt at all. So the front end calls `close_prompt_ack` as it is
about to draw the dialog, the watchdog disarms itself on seeing that, and from
then on the wait is unbounded. Two flags rather than one, because "a question is
outstanding" and "the question is on screen" are different facts and the second
is the one that ends the deadline.

`CLOSE_PROMPT_GENERATION` covers the third case: a watchdog that wakes to find
the number moved is looking at a prompt that is already over — answered, or
superseded by a newer request — and must not close a window on the strength of a
question nobody is asking any more.

Three ways out, and all three clear the same state (`end_close_prompt`):
**minimize**, **close**, and **cancel**. Cancel is not padding. Esc and a click
outside resolve to it, because a prompt with no way out turns one stray click on
the frame into a forced choice between hiding the window and ending every
session — and, mechanically, a dismissal that left `CLOSE_PROMPT_PENDING` set
would make the next press of X read as "already asking" and be ignored, giving a
window that can only be closed once.

`/exit` is the one path that skips the question: typing it *is* the answer, so
`quitApp` ends in `window_destroy`. It ends there rather than at `close()` for
the same reason the prompt's own answer does — `close()` raises another request,
which would ask again.

### 22 · Why `idle` is not news, and why "focused" is not "watched"

The notification rule is small because the ways to get it wrong are all noise,
and noise is what makes people switch a notifier off:

- **A status seen for the first time is never news.** Its value is simply what it
  is; at start-up there would otherwise be one notification per open session.
- **`idle` notifies only when a turn was really running the moment before.** It
  is also where a session that has never been spoken to sits, and where one goes
  after being read. A rule that fired on `idle` would announce nothing having
  happened, twice.
- **`running` is never news.** Work starting is not something to interrupt
  somebody for, and the toast would arrive before the work it announces.

The status itself comes from `selectRowStatus` — the same function behind the
rail's dots, the workspace badges and the board's columns. That is what stops a
notification disagreeing with the dot beside it: there is one definition of
"needs you", and it is not restated in the notifier.

`isWatched` is where multi-session is decided, and it needs **the window to be in
the foreground** as well as the session to be the one on screen. Dropping the
first half is the tempting simplification and the one that breaks the feature: a
turn that ends while the window is minimized leaves its session `idle` (there is
no `unseen` for the session on screen), so a rule that read "on screen" as
"watched" would stay silent at exactly the moment the notification is the only
way to learn the work finished. A third case joins them: a **blocking prompt is
watched wherever its session is**, because the prompt is drawn over whatever
conversation is on screen — but only when it is genuinely rendered, so a request
the session board is holding does not suppress the notification that would
surface it.

Both rules are pure functions in `runtime/notify.ts` and asserted in
`tests/notify.test.ts`, because neither failure is visible: a notification that
should not have been sent looks identical, on screen, to one that should have.

### 23 · Why the right rail grew a head, and where its toggle had to live

The right rail used to begin straight at "Goal". Its five blocks say what is *in*
the rail; nothing said what the rail **is**, and the two rails flanking the
transcript did not read as a pair — the left one opened with a mark and a name,
the right one with a block. So the head is the left rail's head mirrored: the
same title, on the same 42px band.

Two things about it are decisions rather than styling:

- **The title is "Session runtime", not a second "tudouni-aigo".** The left head
  carries the product name because it identifies the window; this head has to
  identify **what the column reports on**, because everything below it —
  goal, tasks, skills, jobs, MCP — is a fact about the session in flight and not
  about the transcript beside it. A repeated product name would have been a
  second copy of the left head's fact and would have said nothing new.
- **Neither head carries a collapse control any more.** Both did, and both were
  the same mistake from two directions: a control that lives *inside* the thing
  it hides cannot perform its own act — pressing it removes the control, and the
  rail comes back only from `Ctrl+B` / `Ctrl+L`, or from a `Show` button that
  exists solely in the collapsed row. `SessionBar` had already solved this for
  the left rail by keeping its toggle outside the rail. That is now the **only**
  place either rail is folded from: one toggle at each end of the session bar,
  both `flex: none` outside the facts' scroller, so neither can be scrolled out
  of reach by a long session id. The trailing one is `disabled` while the session
  board is up, because `showSidebar` is *derived*
  (`sidebarVisible && !hiddenByCss && !boardOpen`) and the key refuses for the
  same reason: writing the preference under the board would change nothing on
  screen and then bring the rail back in the opposite state. A button that
  appeared to do nothing would be the worse half of the same bug, so the two
  agree instead of one of them silently doing nothing.

The two heads are asserted as **one band**, not as two elements: they sit at the
same height on either side of the transcript, so `.rb-head` repeats `.lb-head`'s
42px and its `border-bottom` on purpose, and `render-check.mjs` fails if the two
numbers drift apart. A height difference there shows up as a step at the
transcript's edges, which is the kind of thing that looks like a rendering
artefact rather than a header.

### 24 · Why the board is reachable from two places, and why that is not a duplicate

The session board's button lives in the left rail's foot, beside Files and
Terminal. That is the right shelf — it is a way *out* of the transcript, the same
kind of thing as the other two — and it is the **wrong side of the fold**. The
rail is not unmounted when it is collapsed, it is `inert` (a rail nobody can see
must leave the tab order), so with the rail away the board's only door is behind
a door. That is the failure `SessionBar` was built to end for the rail toggles
themselves, arriving one control over.

So the bar carries a second entrance, one step in from the leading toggle. Three
things about it are decisions rather than styling:

- **It is one control with two doors, not two controls.** The act
  (`setBoardOpen`), the gate and the words are shared, and the gate was *lifted
  out of* `WorkspaceSidebar` for this (`selectBoardAvailable`). A second
  hand-written copy of that condition is the version of this change that would
  go wrong: the two buttons would agree on the day they were written and drift on
  the next edit, and the symptom — one door open, the other dead on the same
  screen — is exactly the "a button that does nothing" report this suite exists
  for. `render-check.mjs` compares the two doors' `disabled` state in the same
  frame, so a future divergence is caught rather than merely unlikely.
- **The gate is the workspace's, not the screen's.** Not `hasSession` (Files and
  Terminal's question) but "some live child in this workspace": the board reports
  on every session at once, so it must open in the case the other two cannot —
  the session on screen is the one whose child failed to start, and the others
  are running fine. That is precisely the screen where somebody needs to see that
  the other sessions are alive.
- **It reads as a toggle, and it stays enabled while the board is up.** It wears
  the two rail toggles' square, because all three fold something away from this
  row and a differently-shaped control in the same run would read as one more
  fact. `aria-pressed` carries the state, and `--accent-subtle` with a real
  foreground colour carries it visually — the accent rather than the neutral
  hover, because this one describes what the whole column is currently showing,
  where the rail toggles point at nothing on screen. Its `disabled` is
  `blocked || (!boardAvailable && !boardOpen)`: the trailing clause is what keeps
  an open board from being a room with no door when its last child exits.

The button sits **outside `.sb-scroll`**, like the toggles and for the same
reason — which here is stronger: with the left rail folded this is the only way
to the board, so a long session id must not be able to scroll it off the edge.
`render-check.mjs` asserts its index in the bar's own children rather than merely
its existence, because "right of the collapse button" is the whole request and a
button appended after the facts would render, work, and be in the wrong place.

### 5 · Why the status bar's numbers no longer wait for a turn to end
Decision 5 said the usage, cache and elapsed figures come from `ui(status)`,
requested when a turn ends. That is still where the *session totals* come from —
but it made the bar report the **previous turn's** figures for the whole of the
next one, so a long turn sat still and then jumped. A turn that grew to 300k
tokens showed the entire jump at once.

The fix does not poll more. `model_call` already carries the same four fields —
`prompt_tokens`, `cached_tokens`, `completion_tokens`, `duration_ms` — and the
reducer was already reading them to draw the model row. So the last **successful**
call is now recorded as it lands (`liveCall`, from `reduceEvent`'s `lastCall`) and
the bar reads it, which is exactly what the terminal front end does
(`internal/frontends/tui/model.go` writes the same four into `m.panel` per call).
Three rules travel with it:

- **All four fields are written on every successful call**, to a value or to
  `null`. A call that reports no usage block *clears* the record instead of
  leaving the previous call's count standing, so the pair on screen always
  describes one call. The TUI states the same rule, and
  `TestASuccessfulCallMissingAFieldClearsThatHalf` is why.
- **A failed attempt changes nothing.** A retry carries no usage, so a backoff
  between two attempts leaves a real measurement up rather than blanking it.
- **The cache chip is one call's ratio**, not the session average — the same
  division the TUI's `cacheHitText` does. The `/status` screen still reports the
  session totals, and the two are labelled apart on purpose.

The elapsed figure needed one more thing, because the runtime sends no duration
until `run_finished`: a running turn is timed against a local stamp taken when
`run_started` landed (`turnData.startedAt`, mirroring the TUI's), and the clock
ticks **only while a turn is in flight** (`useTurnClock`). A finished turn reads
`lastTurnMs` — the runtime's own `duration_ms` — so it stops climbing instead of
growing for as long as the window is left open.

`ui(status)` remains the source for a session whose calls this window never saw: a
`/resume`d conversation rebuilds its transcript from the session file rather than
replaying events, so there is no `model_call` to read.

### 6 · Why the rail is not capped, and why `step n / N` is not a fraction

Both of these were inherited from the terminal front end, where the constraint
that produced them is real. Neither constraint exists here.

**The rail's blocks list every row.** The TUI caps a block at `railMaxRows` and
folds the rest into `(+N more)` (`internal/frontends/tui/rail.go`) because its
rail is a **fixed-height column, not a scroll container** — the comment says so
outright: what does not fit can only be cut, or a block becomes unreachable. The
desktop rail is a scroll container (`.sidebar-inner` is `overflow-y: auto`), so
cutting rows hides content the reader could simply have scrolled to. The unifying
rule is still "nothing is silently truncated": rows may not be hidden with CSS,
only scrolled to.

**The status bar reports cumulative steps, with no denominator.** `session.steps`
is `ui(state).steps` — the count of `assistant` messages in the whole session
(`Session.StepCount()`), so it only ever grows and a resumed session starts high.
`session.maxSteps` is `init.max_steps` — `--max-steps`, the budget for **one
turn**, which the agent's loop resets every turn (`internal/agent/agent.go`).
Pairing them printed `step 497 / 120`. Per-turn progress is the turn head's job
and already shows `entry.step / entry.maxSteps`; the cap itself stays where it
belongs, on the session bar (`step cap`) and in the settings panel (`--max-steps`).

### 15 · The rail's MCP row, and why it is narrower than the panel's

The right rail already answered "which servers are configured, which are
running"; the next question — "then start it" — was a `/mcp` command away. So
the action moved onto the row.

The rail is **233px** wide, and **201px** once the window narrows past 1180px
(the rail drops to 236px there). Measured with the real stylesheet, before
anything was added:

- the panel's wording for the not-running state, `configured, not running`, is
  **131px** of a 233px row on its own;
- the row **already overflowed** at 1180px by 25px, squeezing the tools count to
  0–1px.

Adding a button to that leaves no room for both the tools count and the long
state word: keeping them overflows at *every* width (39px at 1440), and an
overflowing row is clipped — the button ends up past the edge where nothing can
click it. The choices that fit keep either the tools count *or* the long state
word, never both.

So the rail shows `name · state · action`, and:

- the **tools count stays in `/mcp`**, where the panel has room for it;
- the state uses its short form, which is the runtime's own word
  (`mcp.not_loaded`, "not loaded") — the same fact in the same vocabulary, not a
  second one;
- the button is `flex: none`. `.btn` is `flex-shrink: 1` by default, and without
  the pin the row squeezes the button to 13–16px instead of 22px: still on
  screen, no longer a usable target.

`mcpPending` is **not** an optimistic update: it records that this front end has
just sent a request, never what a server's state is. The badge still comes only
from `ui(state)`, and the mark is released by the runtime's own `ui(mcp)` reply
(or by `runtime_exited`, so a dead child cannot leave a button disabled by an
answer that will never come).

`scripts/render-check.mjs` asserts all of it: both action words render, each
button's accessible name contains its server, the button keeps ≥22px, the row
does not overflow, and pressing "Load" reaches `mcpPending` without touching
`uiState`. The overflow and the label-interpolation checks are there because
both failures are invisible otherwise — a clipped control still renders, and an
unfilled `{name}` is still a non-empty string.

### 25 · Why connecting to a remote workspace begins with a connection

The first version of the remote-workspace form asked for nine fields at once — a
host, a port, a user, key paths, a password, a workspace directory and a runtime
binary path — and saved them **without connecting**. Every one of those is a
question only the far end can answer, so filling that form in was guessing:

- it could not say whether the credentials work, so a typo arrived later as a
  dead session;
- it asked for a workspace directory as **free text**, which on a machine you are
  not sitting at means inventing an absolute path and only finding out on connect;
- it asked where the runtime binary was — a question with no sensible answer
  before connecting, because whether one is installed is a fact about the host;
- it asked for a host, a port and key paths that `~/.ssh/config` already holds.

So the flow is now three steps, in the order the answers arrive. **1. Which
host** — a list read from `~/.ssh/config`, which is the one place a host is
configured, plus "add a new one" that appends a `Host` block **to that same
file** so the person's own `ssh` gets it too. **2. Connect** — one dial, after
which the far end reports its home, its platform, whether the Runtime is
installed and at which version, and whether it has a usable `config.json`. A
failure is a sentence here, while the form is still on screen. **3. Which
directory** — a browser over the real directories on that host, starting at its
home, with "new folder" for one that does not exist yet. Only then is anything
saved.

Three things about it are decisions rather than layout:

- **Nothing is saved before step 3.** The host and the workspace are written
  together, at the end, once both are known to be real — so abandoning the
  wizard leaves nothing behind, which is what a Cancel button is for.
- **The password is never written to `~/.ssh/config`.** `Password` is this
  project's own extension rather than an OpenSSH keyword: writing it would make
  `ssh` refuse to start for the **whole file**, on every connection to every host
  in it, with `Bad configuration option: password`. It lives in this
  application's own preferences, the existing documented trade-off.
- **The exact block is shown before it is appended.** This is somebody's own
  configuration, often hand-edited and often old, and a wizard that appends to it
  without showing the block is asking for trust it has not earned. The preview and
  the write go through one definition of the format on the Rust side
  (`ssh_config::host_block_lines`); the TypeScript mirror is pinned by its own
  test, and the duplicate rule is asserted there because a `Password` line is
  invisible on screen until somebody's `ssh` stops working.

### 26 · Why the remote runtime runs non-blocking, and why that is not a detail

Every remote session used to hang at "handshaking" with a perfectly healthy
runtime on the far end, and the window froze with it. The cause was a three-way
deadlock built out of one shared lock and libssh2's **blocking** mode:

1. the stderr reader took the channel lock and blocked in `read()`. A remote
   runtime writes nothing to stderr, so on an idle session this never returned;
2. the wait loop took the bridge lock and called `try_wait`, which needs the
   channel lock — blocked, still holding the bridge lock;
3. `runtime_stderr` is a **synchronous** Tauri command reached from the WebView,
   so it needed the bridge lock too — and the renderer's main thread stopped,
   which is why the window froze completely;
4. the stdout reader needed the channel lock — blocked. The runtime's own opening
   `init` was therefore never read, and the session sat in `handshaking` forever.

The repair is a discipline rather than a lock: the session is put in
**non-blocking** mode once the command has started, and every read and write
loops on `WouldBlock`, **releasing the lock between attempts**. No call waits on
the network while holding the lock, so no thread can starve another.

Two consequences worth knowing before touching `ssh_backend.rs`:

- **The channel is not thread-safe and the lock is the only thing making it so.**
  `ssh2::Stream` locks an *internal* mutex per call, which does not serialise one
  `Channel` used as stdin, stdout and the exit control plane at once. Removing the
  outer lock reintroduces the deadlock in a form that looks like a hang.
- **A connect timeout is not a read timeout.** Bounding reads would mistake an
  idle conversation for a dead one; `POLL_INTERVAL` is a yield, and nothing in
  that loop ever gives up on a live channel.

The visible symptom of the original bug is worth recognising, because it looks
like a network problem and is not: window frozen, remote process running fine,
session stuck at `handshaking`, no stderr.

### 27 · Three more faults the remote path was hiding

Each of these was invisible until a window was driven against a real server, and
each is the kind of thing a type check cannot see.

- **The remote command never entered the workspace.** A non-PTY SSH exec starts
  in the account's home directory, and the runtime refuses the home directory as
  a workspace (`paths.UnsafeWorkspace`) — so **every** remote session died on
  start-up with "this cannot be the workspace: /home/<user>", whichever directory
  had been chosen. `RemoteAttachOptions.remote_workspace` was accepted and then
  never used; the local path has always set its working directory explicitly
  (`Command::current_dir`) and this is its remote equivalent. The command is now
  `cd <workspace> && exec <binary> …`, with `&&` so a directory that does not
  exist fails as a refusal to start rather than as a session quietly opening in
  the home directory.

- **Every `Host` block in `~/.ssh/config` was silently dropped.**
  `ssh_config::parse_line` returned the keyword verbatim while every comparison
  downstream tested the lower-case form, and OpenSSH keywords are
  case-insensitive — so a file written the way OpenSSH documents it
  (`Host`, `HostName`) parsed as having **no hosts at all**. The picker was
  empty, `Match` was never noticed and `ProxyJump` was never refused. Nothing
  threw; the list was just blank. The fold now happens once, in `parse_line`,
  which is the single point every line passes through; the value is never folded,
  because a hostname, a path and a user name are all case-sensitive.

- **The config-sync question was asked and then ignored.** `enterRemoteWorkspace`
  called `checkConfigSync` and carried straight on, so the prompt was raised
  **and** the session opened against the remote file the person had not yet
  decided about — the decision arrived after the thing it was meant to decide. On
  a fresh remote account (no usable route in its `config.json`, the ordinary
  first case) the session died with exit code 2 while the question was still on
  screen, and answering it changed nothing. The open is now parked in
  `pendingRemoteOpen` and resumed by the answer.

Two smaller ones, both about a remote path being treated as a local one:
`lastWorkspace` was written from a remote session's `init.workspace`, so the next
launch would try to open a directory that only exists on the server; and the
left rail's `currentWorkspace` fed a remote path into the **local** workspace
list, adding a row that could only ever fail and marking the same place current
twice.

## Verification

**Three gates, all of them required**, and the last two need something a plain
unit test cannot provide:

```bash
npm run typecheck     # tsc -b, zero errors
npm test              # the protocol, the projection, the reducer, the stylesheet rules
npm run audit:css     # every className has a CSS rule
```

The unit tests exist because **protocol mismatches are the easiest thing to get
wrong and the hardest to see**: a wrong key name does not throw, it renders as
blank or as 0, and the screen looks plausible.

`class-audit.mjs` catches the sibling failure: a `className` with no matching CSS
rule. Nothing else can see it — the element renders, it is just unstyled, so a
control lands in the wrong place and only a screenshot shows it.

**Before a release, these as well.** They need a running runtime or a browser, so
none of them is in `npm test`:

```bash
# 1. Against the real binary.  <exe> <workspace> are both required.
npm run test:e2e -- <abs-path-to-tudouni-aigo> <abs-path-to-workspace>

# 2. Against the rendered interface, with `npm run dev` and a CDP browser up.
node scripts/render-check.mjs http://127.0.0.1:5178/ 9333

# 3. Can a person actually click the window controls?  Same prerequisites.
npm run check:window -- http://127.0.0.1:5178/ 9333

# 4. Does X ask, and does a session behind the window say so?  Same prerequisites.
npm run check:close-notify -- http://127.0.0.1:5178/ 9333

# 5. The add-remote-workspace wizard, over real SSH to a real host, in the real
#    window.  <port> <host> <user> <password> [directory] — the app must be
#    running with remote debugging on <port> (see "Known boundaries" below).
node scripts/remote-workspace-e2e.mjs 9333 192.168.1.200 tudouni <password> [dir]

# 6. Is that remote session a *working agent*, or merely connected?  Sends one
#    real turn and lists the remote workspace's own files.  Same prerequisites.
node scripts/remote-agent-smoke.mjs 9333 "Reply with exactly: REMOTE OK"
```

**Against the real binary.** Starts `tudouni-aigo --runtime-stdio` the way the
Rust bridge does and decodes the output with the same decoder the UI uses. It
asserts the opening triple (`init` -> `session_load` -> `ui(state)`), that every
`init` and `ui(state)` field the UI reads is present, that empty lists arrive as
`[]` and never `null`, that a malformed line and an unknown type are both skipped
without breaking the stream, and that a requested shutdown exits with code 0.

It also walks the workspace's two capabilities end to end — `file_list` →
`file_read` → a **refusal** (which arrives as a `notice`, not as a `ui(files)`,
and is the path a front end forgets), then `terminal_create` → `terminal_resize`
→ `terminal_kill` → `terminal_close`.

Two rules about this script, both learned the hard way:

- **It compares `init.protocol` against `PROTOCOL_VERSION`, never a literal.** It
  used to assert `3` while `src/protocol/types.ts` said `4`: two declarations of
  one fact, each with a test backing it, and the wrong one was the one nobody
  ran. Any second literal reintroduces exactly that.
- **It needs a binary built from the current tree.** A stale one under
  `src-tauri/runtime/` tests the old runtime and reports the difference as a
  front-end bug — which is what happened the first time this ran after
  `terminal_close` was added. `npm run runtime:stage` warns when it cannot find a
  build matching `VERSION`, and that warning is worth reading.

**Against the rendered interface.** With `npm run dev` and a CDP-enabled browser
running, mounts the real tree, records every console error and uncaught
exception, then feeds the **actual store instance** real protocol payloads and
asserts what the DOM did:

```bash
node scripts/render-check.mjs http://127.0.0.1:5178/ 9333
```

It covers the mount itself, all five sidebar blocks in their fixed order, the
opening `init` (including that a runtime notice is rendered verbatim and is not
lost behind the first screen), a full turn (turn head, model step, reasoning,
tool call and result, streamed body, final answer replacing it), both blocking
modals — including that "Always allow" is absent when `remember` is null and
"Allow all" is absent when `allow_trust_all` is false — the 17-command palette,
quiet mode, and the theme following the system.

It writes `render-check.png`; look at it. Two of the defects this project had
(the window controls sitting next to the title, and a turn head reading "in
progress" over a finished answer) were invisible to every assertion and obvious
in the image.

**What would a find-in-conversation cost, and would a highlight even paint?**
`find-proto` is a **prototype, not a release gate**, and it exists because the
mechanism a Ctrl+F layer would rest on cannot be asserted in Node: highlights are
live `Range`s over text nodes React owns.

```bash
node scripts/find-proto.mjs http://127.0.0.1:5178/ 9333
```

It seeds 80 restored turns plus one live turn (548,188 characters of text), then
measures what the layer above the match model has to be built out of. The numbers
it printed are quoted in the script's own header; the four that changed the design
were:

- **A scan over the whole transcript costs 8.2ms and forces no layout**
  (`scrollHeight` 38,240 before and after), so `content-visibility: auto`'s saving
  is not spent by searching. Rescanning a single row costs nothing measurable.
- **The CSS Custom Highlight registry lies.** After a commit replaces a row,
  `size` and `isConnected` both report the ranges as healthy (`registry: 4,
  connected: 4`) while every one of them is empty and draws nothing (`live: 0`).
  React rewrites a text node rather than mutating it, which moves each range's
  boundary to an ancestor. So the paint has to be rebuilt for the rows whose text
  changed, and the hit count has to come from the model — never from the registry.
- **A match inside a folded body has an ordinary rect** (`rectHeight: 17`) while
  sitting in a clip box `0px` tall. "Hidden" is the folding ancestor, not an empty
  rect.
- **The height estimate is 1.55x wrong** (38,240px reported against 59,256px real),
  which is why a jump uses the turn rail's `is-landing` technique rather than
  arithmetic on measured offsets.

**Does `Ctrl+F` find things, and does it stay out of the way?** `find-check` drives
the bar with **real key events** (`Input.dispatchKeyEvent` for `Ctrl+F`, `Enter`,
`Shift+Enter` and `Esc`; `Input.insertText` for the needle, so the box's `onChange`
runs exactly as it does for a person) against a six-turn conversation several
screens tall:

```bash
node scripts/find-check.mjs http://127.0.0.1:5178/ 9333
```

The four things it is for, none of which a unit test can see:

- **`Ctrl+F` is wired to it at all.** The key was previously swallowed by
  `useGlobalKeys`'s reload-key guard, and that guard runs before the terminal
  check — so taking it off that list is a one-line change whose failure mode is
  "the key does nothing".
- **The mark is live and where the reader is looking.** The registry is asked
  (`CSS.highlights.get`) and each range's own rect is compared against the
  scroller's viewport, because a commit that rewrites a text node leaves ranges
  that still count and draw nothing.
- **A row whose `data-entry` element is its own content container is searched.**
  This is the bug the check found on its first real run: `contentOf` looked for the
  container among the row's *descendants*, so `.e-user` and `.e-stream` — a prompt,
  and the body currently being written — were skipped entirely. A prompt is what
  people search a transcript for most, and the hit was not miscounted, it was
  invisible.
- **`Esc` closes the search instead of interrupting the turn**, and a streamed
  chunk does not drag the reader off the hit they are on. The chunk test prints a
  per-chunk `scrollTop` trace: the one adjustment it makes is 20px, once, on the
  sixth chunk (scroll anchoring), not a per-chunk follow.

**Can a person actually click the window controls?** `check:window` answers that
one question, and it is the check most likely to regress silently: every other
gate passes while the buttons are dead, because the markup is right and a modal
layer is simply over them.

```bash
npm run check:window -- http://127.0.0.1:5178/ 9333
```

It installs a fake `__TAURI_INTERNALS__` that records every `invoke`, mounts
Tauri's **own** `drag.js` from the pinned crate, then clicks each control with
**CDP's real mouse events** — not synthetic `.click()` — in three states: nothing
open, a `/files` panel open, and a blocking approval modal up. It also
double-clicks the title text and asserts the window really ends up maximized.

Two things about it are the point rather than the plumbing:

- **Real mouse events, not `.click()`.** A synthetic click is delivered straight
  to the element and bypasses hit testing, so it reports success on a button a
  person cannot reach. The first probe that found this bug used synthetic clicks
  and reported everything fine; the failure only appeared with real ones. Never
  verify "can somebody click this" with a method that skips hit testing.
- **The two overlays have opposite expectations, and both are correct.** Over a
  **panel**, clicking the frame sends the command *and* dismisses the panel —
  that is what an outside-pointer event means to a dialog, and a panel that
  stayed up would be the one state where the frame does nothing. Over the
  **approval modal** the prompt must stay up: a stray click is not a decision.
  Anything touching an overlay's `z-index` can flip both, and nothing on the page
  looks different when it does.

**Does X ask, and does a session behind the window say so?** `check:close-notify`
answers both new decisions, and it is the check that needs the most from the fake
host:

```bash
npm run check:close-notify -- http://127.0.0.1:5178/ 9333
```

It drives `window://close-requested` into the page **from the harness** — the
event is emitted by Rust, so nothing the page does can produce one — and asserts
the four ends of the close rule: the prompt is raised and acknowledged, Esc
resolves to `cancel` (and clears the state, so the *next* X still works), a
remembered choice answers without raising anything, and a dismissal destroys no
window. Then it counts notifications across the transitions that matter: a
session seen for the first time, a background finish, a request that arrives with
the window minimized, and the two cases that must stay **silent** — a prompt
already rendered in front of the person, and a session merely returning to idle.

Three traps, all of which cost real time here and all of which are the harness
being wrong rather than the application:

- **`unlisten` needs `__TAURI_EVENT_PLUGIN_INTERNALS__`.** The real `_unlisten`
  calls `window.__TAURI_EVENT_PLUGIN_INTERNALS__.unregisterListener` *before* it
  invokes anything. A fake host that omits that object makes every `unlisten()`
  throw on its first statement, so the listener is never removed — and under
  StrictMode's mount / unmount / remount the **cancelled** closure is the one an
  event reaches. Its writes are skipped by design, so a perfectly working hook
  looks like a broken one. The failure that exposed this was "a minimized window
  is not notified"; the measurement that identified it was `is_focused` returning
  `false` while the hook's own ref still read `true`.
- **Listeners are keyed by id, not by name.** A registry with one slot per event
  name drops the live listener in favour of a stale one. `__emit` must therefore
  fire at *every* id registered for a name, exactly as the real bridge does.
- **`transformCallback` returns a number; the handler is at `window['_' + id]`.**
  The real backend reaches the callback through that prefixed global. Calling
  `window[id]` looks up `window[7]`, which is nothing at all — and the error
  (`window[handler] is not a function`) points at the harness, not the app.

One more, about the *assertions* rather than the plumbing: an `asking` status is
**not** always worth a notification. A request drawn over the transcript is
already in front of the person, so `isWatched` counts it as seen and silence is
correct — the case that must speak up is a request arriving while the window is
in the tray. Both halves are asserted now, and the focus and minimize conditions
are exercised **separately**: testing them together lets a broken focus path hide
behind a working minimize one.

## Known boundaries

- **Resolved: the window did not open because this repository carried a "Low"
  integrity label.** The symptom was a process that exited during start-up with
  no window, and a `launch.log` holding either

  ```
  Failed to setup app: Access is denied. (os error 5)
  ```

  or the WebView2 spelling of the same thing. The cause was not in this project.
  `C:\Users\XPS\WorkBuddy\tudouni-aigo` — and therefore every file created
  inside it, `target\debug\tudouni-aigo-desktop.exe` included — was labelled
  `Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)` by an AI agent's file
  sandbox. **Windows caps the integrity level of a new process at the label on
  the image file it starts from**, so the app ran at low integrity whoever
  launched it. Low integrity cannot write to `%LOCALAPPDATA%`, and Tauri creates
  the WebView2 user data directory there (`tauri/src/manager/webview.rs`,
  `prepare_webview` → `create_dir_all`): that is where `os error 5` came from.
  WebView2 failing to write the same profile is where the `0x8000FFFF`
  "catastrophic failure" form came from.

  Measured, not reasoned: a fresh copy of `cmd.exe` run from the repository
  reported `Mandatory Label\Low Mandatory Level`, the same copy in `%TEMP%`
  reported `Medium`, and after `icacls <exe> /setintegritylevel Medium` it
  reported `Medium` as well. The label was constant across every failing launch,
  which is why the failure looked intermittent rather than absolute — a launch
  that found a WebView2 profile directory already in place got further than one
  that had to create it.

  The fix is one command, and `scripts/run-desktop.cmd` now checks for the label
  and prints it instead of failing silently:

  ```
  icacls "C:\Users\XPS\WorkBuddy\tudouni-aigo" /T /C /setintegritylevel "(OI)(CI)Medium"
  ```

  With the label cleared the window opens. The process tree is then the one the
  design wants: `msedgewebview2.exe` and `tudouni-aigo.exe` both children of the
  app, and the profile written to `%LOCALAPPDATA%\dev.tudouni.aigo`. A sandbox
  that re-labels this workspace brings the failure back; the check in
  `run-desktop.cmd` is what makes that readable.

- **Resolved: three separate faults sat behind the window being up but empty.**
  Clearing the label got a window that still showed `Starting the runtime…`
  forever, with a healthy runtime behind it. Reading the live DOM over WebView2's
  remote debugging (`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=…`,
  then CDP `Runtime.evaluate` on `document.body.innerText`) is what turned that
  from guesswork into a measurement; every claim below was checked that way, in
  the real window, not in a browser.

  1. **`runtime_attach` was called with the wrong argument shape.** The command is
     `fn runtime_attach(app, options: AttachOptions)`, and Tauri keys arguments by
     parameter name, so the payload has to be `{ options: { … } }` — the front end
     was sending the six fields at the top level. The invoke failed with
     `missing required key options`, nothing caught the rejection, and the child
     was never spawned at all. Fixed in `src/runtime/tauri.ts`.
  2. **The bridge's "the front end is listening" flag lived on the child.**
     `runtime_attach_listener` is called *before* the runtime is started, on
     purpose — the listener has to exist before the child can answer — but with
     the flag inside `Child_` there was nothing to set it on, so the command
     returned `the runtime is not running`, the front end's `catch` swallowed it,
     and every line the child sent stayed in the queue forever. The flag now
     lives in `BridgeState` beside the child, under the same lock, so it can be
     recorded before a child exists and the flush-on-attach race is closed.
  3. **No Tauri v2 capabilities existed at all.** `src-tauri/capabilities/` was
     empty, and Tauri denies every core and plugin command that no capability
     grants — `core:event:allow-listen` among them. `listen()` therefore failed,
     `createTauriRuntime`'s `catch` swallowed that too ("Not hosted, or the host
     refused: the UI stays in its booting phase", which is exactly what it did),
     and the WebView received `init` / `session_load` / `ui(state)` with no
     listener attached. The same omission blocked the directory picker
     (`dialog:allow-open`), so the one workaround for the workspace below was
     dead as well. `src-tauri/capabilities/default.json` now grants `core:default`,
     `dialog:default`, and the four window permissions an undecorated title bar
     needs (`allow-minimize`, `allow-toggle-maximize`, `allow-close`,
     `allow-start-dragging` — `core:window:default` contains none of them).

  All three had the same shape: a real error, swallowed by a `catch` whose
  comment says the UI will just stay in its booting phase. That is worth knowing
  about this codebase — while it is booting, silence means nothing.

  One consequence of starting under `npm run tauri dev`: the app's working
  directory is `src-tauri`, and the workspace *is* that directory, so the session
  runs with no `AGENT.md` and keeps its state in `src-tauri/.tudouni/`. Use
  `scripts/run-desktop.cmd` (it `cd`s to the repository root), or pick the
  workspace in the interface, which restarts the child there.

  Everything below is the record of that hunt, kept because the measurements are
  still true. Ruled out, each by measurement rather than reasoning:
  - the toolchain — cargo 1.98.1, the MSVC linker and Tauri CLI 2.12.0 are all
    installed and working;
  - a missing or stale runtime — it is staged, and `runtime:stage` is repeatable;
  - the WebView2 runtime itself — Windows Search runs on the same build
    (153.0.4234.48) without trouble;
  - the window's own attributes — style, decorations, URL, an explicit
    data directory and the plugins were each varied, and the error was identical
    every time;
  - a bad user-data directory — `create_dir_all` on it succeeds from a minimal
    standalone Rust program, and it succeeds from this app too once the process
    is no longer low integrity. This is the measurement that was missing;
  - AppLocker, SRP, IFEO, exploit-protection mitigations and `WEBVIEW2_*`
    environment variables — all absent. What none of those checks looked at was
    the integrity label *on this directory*, which is not a machine policy and
    leaves no trace in any of those places.

  The misleading part was the "intermittency": about 2 in 9 launches from the
  same shell got through, which sent the search after a process-tree or timing
  effect. There is no timing effect — the label was always there.
- **A retraction.** An earlier revision of this file claimed that registering the
  single-instance plugin first was a fix for the failure above. That was wrong
  and is withdrawn: `tauri::app::setup()` builds the windows before it runs
  plugin setup, so plugin order cannot be on that path. The plugin is still
  registered first — its own documentation asks for that — but it fixes nothing
  here, and the two successful launches that looked like confirmation were
  launches that reused an existing WebView2 profile directory.
- The `dist/` output is a Vite build; it is not a packaged installer. Producing
  one needs `npm run tauri build` on a machine with the Rust toolchain.
- `src-tauri/runtime/` contains only a README. A packaged app needs the runtime
  binary, `prompts/`, `config.example.json` and `tools/vendor/rg/<triple>/` in
  there — the same layout `make release` stages. Point `TUDOUNI_RUNTIME` at an
  existing build to develop against one.
- The icons are **designed, not generated**. `src-tauri/icons/source-icon.png` is
  the hand-drawn rabbit, and the set beside it is produced from that file by
  `scripts/import-icon.ps1` (a one-off, kept because the two fixes it applies —
  the "AI generated" watermark and the white page outside the rounded corners —
  are reproducible from it rather than from memory). The green field with a
  terminal prompt glyph that `scripts/make-icons.mjs` used to generate is **gone,
  script included**: the window's own marks are now the icon file itself, so the
  generator had no consumer left and running it would have silently overwritten
  the rabbit with the old green squares.

## What was found by looking, not by asserting

Three defects survived type checking, the unit tests and the end-to-end protocol
check, and were caught only by mounting the interface in a browser and reading
the screenshot:

1. **The React tree never mounted.** `selectAskOn` and friends returned a fresh
   array on every call, so zustand v5's identity comparison never stabilised and
   the component re-rendered forever. The page was blank. Fixed with `useShallow`
   and shared empty constants — and the reason is written at both sites, because
   the failure mode is invisible.
2. **Runtime notices were dropped behind the first screen.** The design is
   explicit that they are session content and are not squeezed out; a workspace
   whose runtime failed to start showed a friendly greeting and nothing else.
3. **The window controls were styled by no rule at all.** The component asked for
   `.title` and `.window-controls`; the CSS defines `.tb-title` and `.wincontrols`.
   Nothing can see that except a screenshot, which is why `npm run audit:css`
   now exists.

A fourth — a turn head still reading "in progress" over a finished answer, because
the two `run_finished` messages are unordered — was visible in the same
screenshot and is now covered by an assertion in both the unit tests and the
render check.
