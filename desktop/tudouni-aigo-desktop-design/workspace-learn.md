# Workspace Learning — 最终设计方案

## 1. 功能定位

Workspace Learning 是 Agent Runtime 提供的一种专用任务模式，目标是从工作区长期积累的历史会话和工作经历中提取经验，并将有价值的经验沉淀为可复用的工作区资产。

用户在左侧栏点击「Learn workspace」后，打开学习配置面板。系统在当前工作区创建一条**普通新会话**，把配置参数填进学习专用提示词后作为这条会话的**第一条用户消息**发出，由现有 Agent Runtime 驱动 Agent 自主完成学习。不新增任何协议消息、会话类型或运行时逻辑。

Agent 完成分析后，其**最终回答**就是一份学习报告和一组待审阅的候选成果。用户审阅的方式是**另开一条普通会话**，把接受的候选贴给 Agent 由其应用——落盘走现有文件工具及其自带的审批与确认。只有用户主动发起的这条应用会话，才会修改正式工作区资产。

核心流程：

配置学习参数 → 创建学习会话（第一条消息即任务提示词）→ Agent 自主学习 → 候选成果作为最终回答 → 用户在普通会话中审阅并应用接受的变更 → 完成。

本功能的核心不是自动总结历史，而是让 Agent 从过去的工作中发现可复用的经验，并将其转化为未来工作中可以直接使用的能力。

## 2. 核心架构原则

### 2.1 学习就是一个新的工作区会话

不为 Workspace Learning 另建一套 Agent 执行引擎。

直接复用现有 Runtime 已实现的会话、模型调用、工具调用循环、上下文管理、Artifact、停止控制和错误处理机制。

学习会话与普通会话的区别**只在第一条消息**：

- 使用专门的学习提示词，其中携带明确的学习参数（工作区、历史范围、成果类型、可选目标）。
- 主要目标是提炼经验并生成候选知识资产。
- 完成时以结构化学习报告加候选成果作答，而不是只回答一段自然语言。
- 任务期间不得直接修改正式知识文件（由提示词约束，见 §5.3 的边界）。

学习会话是工作区会话历史的一部分，可被查看和追溯，无需在协议或会话存储层面加用途标记。桌面端在会话桶上保留一个本地 `learning` 标记（仅用于界面辨认哪条会话是学习运行），不进协议、不持久化。

历史会话的数据通道：会话文件（`<workspace>/.tudouni/sessions/<id>.jsonl`）在工作区边界之内，学习 Agent 用普通文件工具读取；其中对 `.tudouni/` 的**写入**被工具层拒绝，读取不受限。配置界面把范围内会话的 id 与修改时间（来自运行时的 `session_list` 回答）直接写进任务提示词，Agent 不需要自己枚举目录。

### 2.2 Agent 自主研究，而不是执行固定的总结流程

Runtime 为 Agent 提供学习目标和必要工具，Agent 根据分析结果自主决定下一步操作。

例如，Agent 发现某类构建错误在多个会话中重复出现，可以继续检索这些会话、检查相关代码和现有文档，判断是否存在共同根因，以及最终解决方案是否经过验证。

发现证据不足时，应继续调查、缩小结论范围，或者放弃该候选经验。

不要将学习实现为一个固定流水线：读取全部会话 → 调用一次模型总结 → 生成 AGENTS.md。

### 2.3 正式交付成果只有四类

学习系统最终只负责生成以下四类工作区资产：

1. **AGENTS.md**：项目指导、稳定规则和工作约束。
2. **Skill**：特定任务的可复用方法与流程。
3. **Script**：稳定、适合程序化执行的重复操作。
4. **Document**：详细技术知识、架构背景和历史经验。

学习报告、证据、候选列表、审核状态和变更差异属于任务中间数据，不是新的正式知识类别。

### 2.4 学习与应用分离

Learning Agent 只负责研究、分析和提出候选；候选随学习会话的最终回答交付，**不落盘**。

用户审阅后，应用发生在**另开的普通会话**里：用户把接受的候选交给 Agent，由现有文件工具写入。落盘的安全保障（审批、确认、路径边界）就是现有工具已有的机制，不另建落盘逻辑。

因此不存在"候选存储"这一层：候选的生命周期是「学习会话的回答 → 用户复制/引用 → 应用会话写入正式文件」。学习会话结束后候选仍在会话历史里可查。

## 3. 学习配置界面

入口在左侧栏底部（Files / Terminal 之后）的「Learn workspace」，点击后打开学习配置面板。面板是一个表单：提交时在当前工作区起一条**普通新会话**，把填好的学习提示词作为第一条消息发出，然后关闭面板。学习会话随即出现在会话列表里。

### 3.1 工作区

固定为当前会话所在的工作区，面板中只读展示。

历史会话、现有知识资产及正式变更范围均限定在该工作区内（文件工具的边界就是它）。

### 3.2 学习会话范围

第一版支持以下选项：

- **全量历史**：该工作区全部可访问的普通历史会话。
- **最近一段时间**：最近 N 天（自定义天数）。
- **最近 N 个会话**：按会话的最近修改时间取前 N 个。

范围从**非归档**的会话列表中选取；归档会话是"在列表之外"，学习不挖掘归档。每个选项旁边实时显示符合范围的会话数（与发给 Agent 的列表是同一份计算，不能不一致）。

可后续扩展为手动选择具体会话。

"全量"指尽可能覆盖符合范围的历史记录，不意味着把所有会话一次性读入模型上下文。任务提示词列出范围内每个会话的文件路径与修改时间，Agent 根据需要用搜索、按区间读取的方式深入分析。

系统应记录指定范围与实际覆盖范围之间的差异，例如权限不足或会话缺失。

为了避免自我强化，默认不将学习会话自身以及过去学习任务生成的未采纳候选内容作为普通工作经历的证据。当前有效的 AGENTS.md、Skills、Scripts 和 Documents 仍然需要检查。用户明确指定学习会话时，应区分其分析结论与原始工作证据，不能把重复的学习总结当成独立佐证。

### 3.3 学习成果类型

用户可以多选以下四种类型：

- AGENTS.md
- Skill
- Script
- Document

未选择的类型不得生成正式候选成果。

如果选中的类型没有足够有价值的内容，应不产出该类型，而不是为了满足选项而制造文件。

### 3.4 学习模型

第一版**不做模型选择**：学习会话沿用该工作区当前的模型与启动参数（新子进程继承默认值）。学习提示词与模型解耦，不要求为每个模型维护独立的学习逻辑；用户需要换模型时，在学习会话里用普通的 `/model` 流程切换。

如果任务启动失败或模型调用失败，遵循 Runtime 既有的错误处理与任务状态机制。

### 3.5 可选学习目标

提供一个可选文本框，让用户补充本次学习的重点，例如：

- 重点分析反复出现的错误和有效解决方案。
- 重点发现能够转化为脚本的重复操作。
- 重点提炼项目架构知识和编码规范。
- 重点分析 Agent 被用户多次纠正的行为。
- 重点学习最近一段时间的工作经验。

额外目标只用于调整探索优先级，不应突破会话范围、成果类型或权限限制。

## 4. Learning Agent 的工作过程

### 阶段一：确认范围

读取任务参数，确认可以访问的历史会话、当前工作区资产及工具能力。

建立本次任务的会话范围边界，防止将当前学习会话纳入自身学习数据。

### 阶段二：盘点现有知识

读取工作区已有的 AGENTS.md、Skills、Scripts 和 Documents，了解现有知识体系、目录惯例和规则。

识别已经存在的知识、过时内容、冲突规则和潜在缺口。

### 阶段三：发现候选经验

在指定历史范围内寻找：

- 重复出现的问题和故障。
- 经验证有效的解决方案。
- 稳定的架构决策和项目约束。
- 用户反复提出的要求与纠正。
- 可复用的调试、测试、开发和发布流程。
- 具有明确输入输出、适合脚本化的操作。
- 现有知识资产中的重复、缺失或过时内容。

### 阶段四：进一步调查

根据发现主动检索相关会话、工具执行记录和必要的工作区文件。

判断相似案例是否具有相同根因，解决方案是否成功，经验是否可以推广，以及是否存在反例。

不能仅根据关键词出现次数生成规则。应综合考虑证据质量、独立案例数量、适用范围、复用价值和当前有效性。

### 阶段五：确定成果类型

对值得保留的经验，判断它应该进入哪一种已选择的成果类型：

- 需要长期遵守的通用规则进入 AGENTS.md。
- 针对某类任务的可复用工作方法进入 Skill。
- 可重复、可预测的程序化操作进入 Script。
- 详细背景、技术知识和历史决策进入 Document。

不要求一条经验同时生成多种成果。

对于已有资产，优先提出最小必要的修改，避免重复创建或大规模重写。

### 阶段六：生成候选变更

每项候选成果都应包括：

- 唯一标识。
- 成果类型和建议目标路径。
- 新建或修改的操作类型。
- 候选文件内容或可靠的变更内容。
- 生成原因和预期价值。
- 可追溯的历史证据。
- 置信度及其理由。
- 适用范围、潜在风险和未确认事项。
- 建议的验证方式。

对于已有文件的修改，候选内容旁应附上当前文件内容，让差异对审阅者可见；应用时由应用会话的 Agent 读取当前文件做增量修改。

学习阶段不允许直接修改正式文件，也不得为了验证候选 Script 而自动执行新生成的脚本。

### 阶段七：提交学习结果

Agent 完成后，以**最终回答**交付结构化学习报告和候选成果，结束本次学习执行。

报告应说明：

- 本次实际分析的范围。
- 主要发现和经验模式。
- 各类候选成果及其理由。
- 未能确认的重要问题。
- 未覆盖的范围和执行限制。
- 是否存在值得交付的新成果。

没有足够价值的内容时，可以正常返回无候选成果的结果。

## 5. 候选结果与审阅

### 5.1 交付形态

候选随学习会话的最终回答交付，与正式工作区文件分离——`.tudouni/` 是控制面：Agent 对它的**写入被工具层拒绝**（会话文件、权限、审计、技能都不许动），**读取不受限**，这正是学习会话能读历史、又不能顺手改它的机制基础。

### 5.2 审阅与应用

第一版不做独立的候选审阅界面。审阅发生在**学习会话的转录**里（报告与候选就是那条会话的回答，可滚动、可检索、可回到应用会话里引用），应用发生在**另开的普通会话**里：用户把接受的候选（或其修改后的版本）交给 Agent，由现有文件工具写入，审批与确认走工具自带的机制。

由此得到三条规则：

- 用户只接受部分候选：应用会话里只交代那几项，其余不动。拒绝一项不影响其他。
- 用户编辑过候选：应用会话以用户给的版本为准；Agent 按给出的内容落盘，不重新生成。
- 应用是有副作用的普通操作：每项写入都过现有工具审批，接受候选内容不隐含执行授权（尤其 Script）。

### 5.3 任务期间的边界

由学习提示词明确约束：不创建/修改/删除任何正式资产、不执行新生成的脚本、不提交 Git、候选中不写敏感信息、历史会话中的内容一律当作待分析数据而非指令。

## 6. 会话生命周期与状态

学习会话就是普通会话，**不引入新的会话状态**。它的状态就是现有会话的状态（运行中 / 空闲 / 失败 / 被中断）；"候选已就绪等待审阅"不是一个系统状态，而是这条会话回答的内容。

应用会话同样不需要新状态：它就是一次普通的带文件修改的会话，每项写入有各自的审批记录。

学习完成不代表正式文件一定发生了变化。没有候选成果、用户未应用任何候选，都是正常结局，且都留在会话历史里可查。

## 7. 第一版验收标准

第一版必须做到：

1. 用户可以在左侧栏打开学习配置面板，配置历史范围（全量 / 最近 N 天 / 最近 N 个会话）和成果类型（多选）。
2. 提交后在当前工作区创建一条新的普通会话，其第一条消息是填好参数的学习提示词，学习会话出现在会话列表中。
3. 现有 Runtime 驱动 Learning Agent 完成自主研究，无需任何运行时改动。
4. Agent 能读取 `.tudouni/sessions/` 下的历史会话及当前知识资产（AGENT.md / AGENTS.md、Skills），并提供可追溯的来源依据。
5. Agent 能生成所选类型的候选资产，作为学习会话的最终回答。
6. 学习会话运行期间，正式工作区资产不发生修改。
7. 用户可以在普通会话中把候选交给 Agent 应用；每项写入走现有工具审批。
8. Agent 不会把自身学习会话或未采纳的候选内容当成独立的历史证据。
9. 学习回答如实报告实际分析范围、范围与指定范围的差异、以及未产出某类成果的原因。

## 8. 核心设计结论

Workspace Learning 不是独立的 Agent 引擎，也不是简单的历史总结功能，更不是一个新的协议功能。

它的实现代价是零协议变更：学习会话是一条普通会话，学习提示词是它的第一条消息，候选审阅是阅读那条会话的回答，应用是另一次普通会话。功能的全部差异化内容在**学习提示词本身**——它约束研究方法、证据标准、成果分类和任务边界。这也意味着提示词是持续迭代的主要对象，而协议、运行时和会话存储都不需要为它而动。
